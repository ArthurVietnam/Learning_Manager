# Учебный менеджер

Веб-приложение для ведения личных учебных заданий по фиксированным курсам. Проект выполняется в рамках лабораторного практикума «Практический курс веб-разработки: React, TypeScript, Node и Supabase» (ПГУ им. Т.Г. Шевченко, Физико-технический институт).

**Автор:** Мунтян Артур Олегович, группа 24ПИ1

## Тема и основной сценарий

Учебный менеджер помогает студенту вести личные задания по своим курсам. Пользователь регистрируется или входит по email и паролю, работает со своими личными заданиями (создание, чтение, редактирование, удаление), фильтрует их по статусу, отслеживает сроки сдачи и выходит из учётной записи.

Данные приложения разделены на две сущности:
1. `courses` — публичный справочник учебных курсов в Supabase (доступен для чтения всем).
2. `assignments` — личные записи заданий пользователя в Supabase, защищённые на уровне PostgreSQL через Row Level Security (доступны только владельцу `owner_id = auth.uid()`).

## Модель доступа и схема данных в Supabase (ЛР 6–7)

Схема базы данных состоит из публичного справочника курсов и защищённой таблицы личных заданий:

| Таблица | Назначение | Ключи, связи и индексы | Доступ и RLS-политики |
| :--- | :--- | :--- | :--- |
| `public.courses` | Публичный справочник учебных курсов | `id text primary key` (PK) | **Публичный (чтение всем)**: RLS включён; `grant select to anon, authenticated`; политика `"courses are publicly readable"` `using (true)`. Модификация клиентам запрещена. |
| `public.assignments` | Личные задания пользователей (основная сущность) | `id uuid primary key default gen_random_uuid()` (PK)<br>`owner_id uuid default auth.uid() references auth.users(id) on delete cascade` (FK)<br>`course_id text references public.courses(id) on update cascade on delete restrict` (FK `assignments_course_id_fkey`)<br>Индексы: `assignments_owner_status_idx (owner_id, status)`, `assignments_course_id_idx (course_id)` | **Строго личный (только владелец)**: RLS включён; `revoke all from anon, authenticated; grant select, insert, update, delete to authenticated`. 4 отдельные политики: `"assignments select own"`, `"assignments insert own"`, `"assignments update own"`, `"assignments delete own"` с условием `auth.uid() = owner_id`. |

### Модель доступа (Access Model)

- `courses` читают все пользователи (гости `anon` и авторизованные `authenticated`), изменения запрещены.
- `assignments` читает и изменяет **только владелец строки**:
  - `SELECT`: `using ((select auth.uid()) is not null and (select auth.uid()) = owner_id)`
  - `INSERT`: `with check ((select auth.uid()) is not null and (select auth.uid()) = owner_id)` (по умолчанию `owner_id` выставляется сервером как `auth.uid()`)
  - `UPDATE`: `using ((select auth.uid()) is not null and (select auth.uid()) = owner_id) with check ((select auth.uid()) is not null and (select auth.uid()) = owner_id)` (запрещает менять чужую запись и передавать свою запись другому пользователю)
  - `DELETE`: `using ((select auth.uid()) is not null and (select auth.uid()) = owner_id)`
- Гостевая роль `anon` не имеет никаких прав на таблицу `assignments`.

### Предметные ограничения схемы (CHECK constraints)

- **`public.courses`**:
  - `courses_id_not_blank`: `check (id = btrim(id) and id <> '')` — идентификатор не может быть пустым или содержать пробелы по краям.
  - `courses_name_not_blank`: `check (name = btrim(name) and name <> '')` — название курса обязательно, не пустое, уникальное (`unique`).
- **`public.assignments`**:
  - `assignments_title_length`: `check (char_length(btrim(title)) between 3 and 100)` — длина названия от 3 до 100 символов.
  - `assignments_status_allowed`: `check (status in ('todo', 'in_progress', 'done'))` — допустимые статусы задачи.
  - `assignments_difficulty_allowed`: `check (difficulty in ('easy', 'medium', 'hard'))` — допустимые уровни сложности задачи.
  - `description text not null default ''` — описание задания со значением по умолчанию.
  - `due_date date not null` — календарный срок сдачи.
  - `created_at timestamptz not null default now()` — точное время создания записи.

1. **Создание проекта и настройка Authentication**:
   - Войдите в [Supabase Dashboard](https://supabase.com/dashboard).
   - В разделе **Authentication** → **Providers** убедитесь, что включён вход по **Email**.
   - В разделе **Authentication** → **URL Configuration**:
     - Задайте **Site URL** для локальной разработки: `http://localhost:5173`.
     - Добавьте в список **Redirect URLs**: `http://localhost:5173/**` и `http://localhost:5173`.
   - Если включено подтверждение email (**Confirm email**), при регистрации форма приложения покажет инструкцию с просьбой подтвердить email по ссылке из письма.
2. **Применение миграции схемы ЛР 5**:
   - В Dashboard откройте **SQL Editor** и примените `supabase/migrations/202610260001_initial_schema.sql`.
   - Заполните справочник курсов из `supabase/seed.sql`.
3. **Применение миграции политик владельца ЛР 6**:
   - В **SQL Editor** создайте новый запрос и выполните миграцию `supabase/migrations/202611020001_assignments_owner_policies.sql`.
   - Скрипт назначит значение по умолчанию `owner_id set default auth.uid()`, выдаст права `select, insert, update, delete` роли `authenticated` и создаст 4 политики RLS для `public.assignments`.
4. **Применение миграции связей и индексов ЛР 7**:
   - В **SQL Editor** выполните миграцию `supabase/migrations/202611020002_assignments_relations_and_indexes.sql`.
   - Скрипт переопределяет внешний ключ `assignments_course_id_fkey` с правилом `ON UPDATE CASCADE ON DELETE RESTRICT` и создает составной индекс `assignments_owner_status_idx (owner_id, status)` и индекс внешнего ключа `assignments_course_id_idx (course_id)`.
5. **Настройка локального окружения**:
   - В каталоге `frontend` создайте файл `.env.local` (на основе `.env.example`) и вставьте свои значения `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`.

## Маршруты и защита страниц

Маршрутизация реализована на React Router v7:

- `/` — перенаправление на `/assignments` (`<Navigate to="/assignments" replace />`).
- `/auth` — публичная страница аутентификации (`AuthPage`):
  - Переключение режимов «Вход» и «Регистрация».
  - Контролируемые поля email и пароля, обработка состояний ожидания (`pending`), ошибок и уведомлений.
  - Регистрация с сохранением redirect URL (`options: { emailRedirectTo: window.location.origin }`).
  - Вход через `supabase.auth.signInWithPassword`.
  - При попытке авторизованного пользователя открыть `/auth` выполняется перенаправление на `/assignments`.
- **Защищённые маршруты (обёрнуты в `RequireAuth`)**:
  - Пока сессия проверяется (`status === 'checking'`), отображается статусная плашка «Проверяем сессию…».
  - Если пользователь не авторизован (`status === 'guest'`), выполняется редирект на `/auth` с сохранением исходного пути в `state={{ from: location.pathname }}`.
  - `/assignments` — страница списка личных заданий (`AssignmentsPage`):
    - Загрузка заданий из Supabase через `getAssignments()`.
    - Карточки заданий, плашка статистики, локальный фильтр по статусу.
    - Обработка состояний загрузки, ошибок сети с кнопкой повтора и пустых состояний.
  - `/assignments/new` — страница создания задания (`NewAssignmentPage`):
    - Форма `AssignmentForm` с асинхронным `onSave`.
    - Блокировка кнопки сохранения во время выполнения Promise для исключения дублирования записей.
    - Сохранение черновика при ошибке отправки.
  - `/assignments/:id` — детальный просмотр задания (`AssignmentDetailsPage`):
    - Полная информация о задании, бейджи статуса, сложности и просрочки.
    - Кнопка «Удалить» с подтверждением через `window.confirm` и асинхронным запросом к Supabase.
  - `/assignments/:id/edit` — редактирование задания (`EditAssignmentPage`):
    - Форма `AssignmentForm` с предзаполненными данными задания.
- `*` — страница 404 (`NotFoundPage`) для неизвестных маршрутов.

В каркасе приложения (`AppLayout`) отображается email текущего пользователя и кнопка «Выйти» (`supabase.auth.signOut({ scope: 'local' })`). Временный баннер о хранении в оперативной памяти удалён.

## Сценарий проверки двумя аккаунтами (A и B)

1. **Регистрация и вход пользователя A**:
   - Открыть `/auth`, зарегистрироваться пользователем A (`user_a@example.com`).
   - Войти, создать два задания (например, «Лабораторная 5 по БД» и «Курсовой проект по сетям»).
   - Перезагрузить страницу (F5): задания загружаются из базы данных.
   - Отредактировать одно из заданий, скопировать его ID из адресной строки.
2. **Выход**:
   - Нажать кнопку «Выйти» в шапке.
   - Список заданий мгновенно очищается в `[]`.
   - Попытка открыть `/assignments` перенаправляет на `/auth`.
3. **Повторный вход пользователя A**:
   - Снова войти как пользователь A: все созданные задания на месте с сохранёнными изменениями.
4. **Вход пользователя B и изоляция данных**:
   - Выйти и войти как пользователь B (`user_b@example.com`).
   - В списке пользователя B отображается «Заданий пока нет» (записи пользователя A полностью скрыты).
   - Создать задание пользователя B (например, «Индивидуальное задание B»).
   - Перезагрузить страницу: отображается только задание пользователя B.
5. **Проверка защитных барьеров RLS**:
   - Попытка запросить или обновить чужой ID пользователя A из сессии пользователя B затрагивает 0 строк благодаря политике RLS (`USING`).
   - Попытка отправить при создании чужой `owner_id` пользователя A отклоняется базой данных правилом `WITH CHECK`.
6. **Возврат к пользователю A**:
   - Войти обратно как пользователь A: все записи пользователя A в сохранности, запись пользователя B не отображается.

## Что сделано в ЛР 7 (Полный CRUD, связи и поиск)

- **Миграция связей и индексов (`supabase/migrations/202611020002_assignments_relations_and_indexes.sql`):**
  - Не затронуты применённые миграции ЛР 5 и ЛР 6.
  - Внешний ключ `assignments_course_id_fkey` переопределён с правилом `ON UPDATE CASCADE ON DELETE RESTRICT`. При попытке удалить курс, на который ссылаются задания, база данных отклоняет удаление.
  - Добавлены индексы для поддержки частых сценариев выборки: составной `assignments_owner_status_idx (owner_id, status)` и `assignments_course_id_idx (course_id)`.
  - Шаг 3 из методички пропущен, так как `courses` — это публичный справочник, а не дочерняя таблица с персональными записями.
- **Вложенный запрос связанных данных (Embedded Resource Query):**
  - Сервис `src/services/assignments.ts` запрашивает связанный курс одним запросом через синтаксис PostgREST: `courses(id, name)`.
  - Тип строки `AssignmentRow` расширен свойством `courses: { id: string; name: string } | null`.
  - Функция `fromRow` извлекает название курса из вложенного объекта `row.courses?.name` без необходимости выполнять повторные запросы N+1 для каждой карточки, а при его отсутствии безопасно подставляет значение из справочника или `course_id`.
- **Серверная фильтрация и поиск в Supabase (`getAssignments`):**
  - Единый тип фильтров `AssignmentFilters` (`query: string`, `status: 'all' | AssignmentStatus`, `courseId: 'all' | string`) и константа `emptyAssignmentFilters`.
  - Запрос в БД строится динамически:
    - Текстовый поиск по названию задания: `.ilike('title', `%${query}%`)` (с триммингом пробелов и ограничением длины в 100 символов; символы `%` и `_` воспринимаются PostgREST как шаблоны подстановки).
    - Фильтр по статусу: `.eq('status', filters.status)`.
    - Фильтр по курсу: `.eq('course_id', filters.courseId)`.
    - Сортировка: `.order('created_at', { ascending: false })`.
  - RLS по-прежнему гарантирует, что возвращаются только строки текущего владельца (`owner_id = auth.uid()`).
- **Компонент панели фильтров (`src/components/AssignmentFiltersForm.tsx`):**
  - Хранит независимый локальный черновик (`useState<AssignmentFilters>`), предотвращая отправку сетевых запросов на каждое нажатие клавиши.
  - Содержит текстовое поле с кнопкой быстрой очистки, выпадающие списки статуса и курса с понятными `<label>`.
  - Кнопка «Применить» передаёт очищенные значения в `onApply`.
  - Кнопка «Сбросить» восстанавливает `emptyAssignmentFilters` и выполняет сброс без дублирующих параллельных сетевых запросов.
  - Блокирует элементы управления и выводит индикатор `Загрузка…` во время выполнения запроса (`pending`).
- **Разделение пустых состояний (`src/pages/AssignmentsPage.tsx`):**
  - Вычисляется флаг `hasFilters = query !== '' || status !== 'all' || courseId !== 'all'`.
  - Компонент `AssignmentFiltersForm` остаётся смонтированным на странице всегда (включая состояния `loading` и `error`), наглядно отображая состояние блокировки полей и индикатор `Загрузка…` во время выполнения запроса.
  - Если `!loading && !error && assignments.length === 0`:
    - При активных фильтрах (`hasFilters === true`) отображается состояние поиска (`empty-search-state`): сообщение *«По заданным фильтрам ничего не найдено.»* и кнопка *«Сбросить фильтры»*.
    - При отсутствии фильтров (`hasFilters === false`) отображается базовое пустое состояние (`empty-list-state`): сообщение *«У вас пока нет учебных заданий.»* и кнопка *«Добавить задание»*.
  - Пустые состояния не отображаются до завершения запроса (`loading === false`).
- **Синхронизация CRUD и устойчивость к ошибкам сети:**
  - Реализована сервисная функция `getAssignment(id, courses)` для единичной загрузки задания по ID со вложенным курсом.
  - После создания (`createAssignment`) фильтры сбрасываются в `emptyAssignmentFilters` и список перезапрашивается с вложенным селектом курсов, исключая ситуацию ложного 404 («Задание не найдено») при переходе на созданную карточку, если ранее были активны несовпадающие фильтры.
  - При редактировании (`updateAssignment`) проверяется сохранение записи в текущей выборке; если фильтры исключили обновлённую запись, происходит сброс фильтров для гарантированного отображения сохранённого результата на карточке.
  - При ошибке сети в процессе сохранения форма сохраняет введённый текст черновика, выводит сообщение об ошибке, а флаг `pending` гарантированно сбрасывается в блоке `finally`.
  - Двойной быстрый клик по кнопке сохранения блокируется флагом `pending`.
  - Удаление требует явного подтверждения (`window.confirm`) и при ошибке выводит понятный текст ошибки.
- **Автотесты и качество:**
  - 30 комплексных тестов в `frontend/test/integrity.test.ts`, включая проверку SQL миграции ЛР 7, контракта фильтров, вложенного маппинга `fromRow`, построения запроса `getAssignments` с `ilike` и `eq`, сервиса `getAssignment`, предотвращения двойного запроса на сброс и логики пустых состояний.
  - 0 ошибок и 0 предупреждений в `oxlint`.
  - Чистая production-сборка Vite (`npm run build`).

## Вопросы для защиты ЛР 7

1. **Что гарантирует внешний ключ и чего он не гарантирует?**
   - Внешний ключ гарантирует ссылочную целостность на уровне СУБД: значение `course_id` в строке `assignments` обязательно существует в первичных ключах таблицы `courses`, а удаление/обновление родителя контролируется правилами `ON DELETE` / `ON UPDATE`.
   - Внешний ключ **не гарантирует права доступа**: он не проверяет, разрешено ли текущему пользователю читать или привязывать эту строку (для этого используются политики RLS).
2. **Почему фильтр owner_id не заменяет RLS?**
   - Фильтр в клиентском коде (`eq('owner_id', userId)`) выполняется по желанию клиента. Злоумышленник может скопировать публичный ключ и через curl или DevTools отправить запрос без этого фильтра. Политики Row Level Security (RLS) в PostgreSQL исполняются ядром СУБД на каждый запрос независимо от клиента и делают чужие строки невидимыми.
3. **Где преобразуется ответ базы в тип интерфейса?**
   - В сервисе `src/services/assignments.ts` в функции `fromRow`. Она принимает `AssignmentRow` (snake_case базы и вложенный объект `courses: { id, name }`), извлекает `courses?.name` в `courseTitle` и возвращает строго типизированный интерфейс `Assignment` приложения. Компоненты UI не работают с сырыми структурами PostgREST.
4. **Чем пустой список отличается от отсутствия совпадений?**
   - Пустой список (`hasFilters === false`, 0 записей) означает, что у пользователя в базе данных вообще нет созданных записей; интерфейс предлагает создать первую запись.
   - Отсутствие совпадений (`hasFilters === true`, 0 записей) означает, что записи у пользователя есть, но ни одна из них не подошла под введённую поисковую строку, статус или выбранный курс; интерфейс сообщает о ненайденных совпадениях и предлагает сбросить фильтры.
5. **Когда выбирать CASCADE, а когда RESTRICT?**
   - `CASCADE` выбирается, когда дочерняя сущность не имеет самостоятельного смысла без родителя (например, удаление пользователя каскадно удаляет все его задания, или удаление задачи удаляет её комментарии).
   - `RESTRICT` выбирается, когда родитель является справочником или самостоятельной ценной сущностью (например, учебный курс нельзя случайно удалить, пока на него ссылаются активные задания студентов).
6. **Как WITH CHECK запрещает связь с чужим родителем?**
   - Если бы дочерняя таблица ссылалась на приватного родителя, в политику INSERT/UPDATE добавляется подзапрос `EXISTS (SELECT 1 FROM parent WHERE parent.id = child.parent_id AND parent.owner_id = (SELECT auth.uid()))`. Это гарантирует, что даже зная чужой `id`, пользователь не сможет привязать к нему свою запись. В нашей теме `courses` — публичный каталог, доступный всем, а персональные задания защищены `owner_id = auth.uid()`.
7. **Почему форму очищают только после успешного ответа?**
   - Если очистить черновик формы до подтверждения сервером (или при оптимистичном подходе без сохранения), то при сетевом сбое, ошибке валидации БД или обрыве соединения весь набранный пользователем текст будет безвозвратно утерян. Сохранение черновика при ошибке и сброс только после успешного Promise даёт пользователю возможность исправить ошибку и нажать «Сохранить» повторно.
8. **Как вы проверили сочетание фильтров и сброс?**
   - В интерфейсе: вводился текст поиска по названию, выбирался конкретный статус и курс; проверялось, что запрос в DevTools Network содержит соответствующие параметры `ilike`, `status=eq` и `course_id=eq`. Нажатие кнопки «Сбросить» возвращает `emptyAssignmentFilters` и запрашивает полный список.
   - В автотестах: написан тест `services/assignments.ts getAssignments applies search query (ilike), status, and courseId filters to PostgREST request`, проверяющий цепочку методов Supabase-клиента при различных комбинациях фильтров, включая пустые значения и пробелы.

## Использование ИИ

ИИ использовался в качестве ассистента для подготовки миграции внешнего ключа и индексов, составления автотестов серверной фильтрации и вложенного маппинга, а также архитектурной проработки разделения пустых состояний. Самостоятельно проверены: выполнение миграции, работа серверных фильтров по 3 параметрам, сброс фильтров, вложенный запрос без N+1, устойчивость формы при сетевых сбоях и успешное прохождение всех 26 автотестов.
