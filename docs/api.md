# Контракт HTTP API (Лабораторная работа 8)

Документация легковесного бэкенд-сервиса на Node.js, TypeScript и Express, обслуживающего расчёт сводки по учебным заданиям.

> **Важное архитектурное примечание:**  
> Маршрут `POST /api/summary/:kind` в ЛР 8 выполняет чистый серверный расчёт на основе переданного клиентом массива открытых записей. Сервер проверяет типы и формат даты во время выполнения, но не обращается к базе данных и не требует авторизационных токенов.  
> В **ЛР 9** этот маршрут будет заменён авторизованным серверным обращением к базе данных Supabase (`React → Node → Supabase`).

---

## Общие параметры взаимодействия

- **Базовый URL разработки:** `http://localhost:3000`
- **Протокол:** HTTP/1.1
- **Формат обмена:** `application/json` (кодировка UTF-8)
- **Лимит тела запроса:** `100kb` (`express.json({ limit: '100kb' })`)
- **CORS:** Настроен для источника, указанного в переменной окружения `FRONTEND_ORIGIN` (по умолчанию `http://localhost:5173`), разрешены методы `GET` и `POST`, заголовок `Content-Type`.

### Формат ответов

- **Успешный ответ предметного ресурса:** всегда оборачивается в объект с ключом `data`:
  ```json
  {
    "data": { ... }
  }
  ```
- **Служебный ответ проверки работоспособности (Healthcheck):**
  ```json
  {
    "status": "ok"
  }
  ```
- **Единый конверт ошибок:** при ошибках 400, 404, 413 и 500 клиенту возвращается стандартизированная структура:
  ```json
  {
    "error": {
      "code": "VALIDATION_ERROR | BAD_REQUEST | PAYLOAD_TOO_LARGE | NOT_FOUND | INTERNAL_ERROR",
      "message": "Человекочитаемое описание ошибки"
    }
  }
  ```
  Ответы сервера никогда не раскрывают stack trace, абсолютные пути к файлам или детали реализации.

## Маршруты

### 1. Проверка работоспособности сервиса (Health Check)

Используется для проверки доступности процесса Node API до отправки предметных данных.

- **Метод:** `GET`
- **Путь:** `/api/health`
- **Заголовки запроса:** не требуются
- **Тело запроса:** отсутствует

#### Пример успешного ответа (`200 OK`)

```json
{
  "status": "ok"
}
```

---

### 2. Расчёт сводки по заданиям

Принимает массив задач, проверяет типы полей, вычисляет опорную текущую дату на сервере и возвращает агрегированные показатели.

- **Метод:** `POST`
- **Путь:** `/api/summary/:kind`  
  *(в ЛР 8 поддерживаются параметры `:kind = tasks` или `:kind = assignments`)*
- **Заголовки запроса:**
  - `Content-Type: application/json`

#### Структура тела запроса (Request Body)

```json
{
  "items": [
    {
      "status": "todo",
      "dueDate": "2026-09-30"
    },
    {
      "status": "in_progress",
      "dueDate": "2026-09-21"
    },
    {
      "status": "done",
      "dueDate": "2026-09-20"
    },
    {
      "status": "todo",
      "dueDate": null
    }
  ]
}
```

#### Правила валидации элементов

| Поле | Тип | Обязательность | Допустимые значения / Формат |
| :--- | :--- | :--- | :--- |
| `items` | `Array` | Обязательно | Массив объектов; длина от 0 до 500 элементов включительно. |
| `items[i].status` | `string` | Обязательно | Одно из трёх строковых значений: `'todo'`, `'in_progress'`, `'done'`. |
| `items[i].dueDate` | `string \| null` | Обязательно | `null` (если срок не установлен) либо календарная дата формата `YYYY-MM-DD` (валидная дата по григорианскому календарю). |

#### Логика расчёта показателей

- **`active`**: количество задач со статусом, отличным от выполненного (`status !== 'done'`).
- **`completed`**: количество задач со статусом «выполнено» (`status === 'done'`).
- **`overdue`**: количество незавершённых задач с установленным сроком, который строго меньше сегодняшней календарной даты сервера (`status !== 'done' && dueDate !== null && dueDate < today`).

#### Пример успешного ответа (`200 OK`)

```json
{
  "data": {
    "active": 3,
    "completed": 1,
    "overdue": 1
  }
}
```

#### Примеры ошибок

- **Синтаксическая ошибка JSON (`400 Bad Request`):**
  ```json
  {
    "error": {
      "code": "BAD_REQUEST",
      "message": "Неверный формат JSON"
    }
  }
  ```

- **Ошибка валидации структуры тела (`400 Bad Request`):**
  ```json
  {
    "error": {
      "code": "VALIDATION_ERROR",
      "message": "items должен быть массивом до 500 элементов"
    }
  }
  ```

- **Ошибка валидации полей элементов (`400 Bad Request`):**
  ```json
  {
    "error": {
      "code": "VALIDATION_ERROR",
      "message": "Проверьте поля элементов"
    }
  }
  ```

- **Превышение максимального размера тела запроса (`413 Payload Too Large`):**
  ```json
  {
    "error": {
      "code": "PAYLOAD_TOO_LARGE",
      "message": "Превышен максимальный размер тела запроса (100kb)"
    }
  }
  ```

- **Неподдерживаемый вид сводки (`404 Not Found`):**
  ```json
  {
    "error": {
      "code": "NOT_FOUND",
      "message": "Вид сводки не найден"
    }
  }
  ```

---

### 3. Обработка неизвестных маршрутов (Fallback 404)

Любой запрос по неподдерживаемому пути перехватывается маршрутизатором до глобального обработчика ошибок.

- **Код ответа:** `404 Not Found`
- **Тело ответа:**
  ```json
  {
    "error": {
      "code": "NOT_FOUND",
      "message": "Маршрут не найден"
    }
  }
  ```

---

### 4. Непредвиденные ошибки сервера (500 Internal Server Error)

Любое необработанное исключение логируется в консоль сервера с полным stack trace, а клиенту отдаётся безопасный стандартизированный ответ:

- **Код ответа:** `500 Internal Server Error`
- **Тело ответа:**
  ```json
  {
    "error": {
      "code": "INTERNAL_ERROR",
      "message": "Ошибка сервера"
    }
  }
  ```
