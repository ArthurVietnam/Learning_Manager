# История этапов

## ЛР 1. Старт проекта на React и TypeScript

Создан каркас приложения «Учебный менеджер» на React + TypeScript + Vite в папке `frontend`. Стартовый экран шаблона заменён собственным: название, описание и заглушка раздела «Мои задания». Удалены счётчик, логотипы и иконка Vite. Проект сохранён в едином Git-репозитории.

### Как проверить

1. Выполнить `cd frontend`, `npm ci`, `npm run dev` и открыть адрес из терминала: виден экран «Учебный менеджер».
2. Заменить в `src/App.tsx` значение `appTitle` числом и выполнить `npm run build`: сборка завершается ошибкой типов. Вернуть строку.
3. Выполнить `npm run build`: проверка типов и сборка проходят.
4. Выполнить `npm run preview` и открыть адрес из терминала: виден тот же экран из готовой сборки.
5. Клонировать репозиторий в новую папку и повторить `npm ci` и `npm run build`: проект собирается без переноса файлов.

## ЛР 2. Страницы приложения и навигация

Внедрена декларативная маршрутизация с использованием библиотеки `react-router` (v7), создана модульная структура страниц и компонентов приложения «Учебный менеджер»:

1. **Типизация данных (`src/types/`):**
   - `Course`: интерфейс курса (`id`, `title`, `code`, `description`).
   - `Assignment`: интерфейс учебного задания (`id`, `title`, `description`, `courseId`, `courseTitle`, `dueDate`, `status`, `difficulty`).
   - `AssignmentStatus` (`'todo' | 'in_progress' | 'done'`) и `AssignmentDifficulty` (`'easy' | 'medium' | 'hard'`).
   - Словари понятных русскоязычных названий статусов (`STATUS_LABELS`) и уровней сложности (`DIFFICULTY_LABELS`).
   - Все типы импортируются через `import type` согласно правилу `verbatimModuleSyntax`.

2. **Мок-данные (`src/data/`):**
   - `COURSES`: фиксированный справочник из 5 реалистичных курсов.
   - `ASSIGNMENTS`: список из 7 реалистичных учебных заданий с уникальными идентификаторами, привязкой к курсам, дедлайнами и статусами. Охватывает все категории: выполненные, в процессе, к выполнению и просроченные.

3. **Компоненты и страницы (`src/components/`, `src/pages/`, `src/app/`):**
   - `AppLayout`: единый каркас приложения с заголовком «Учебный менеджер», панелью навигации на базе `NavLink` с индикацией активного маршрута и областью вывода дочерних страниц `<Outlet />`.
   - `AssignmentsPage`: страница со списком заданий, выводом карточек через `AssignmentCard`, плашкой агрегированной статистики по заданиям (всего, выполнено, в процессе, к выполнению, просрочено), обработкой пустого состояния и кнопкой перехода к созданию задания. Поддерживает пропс `assignments` для изоляции тестов.
   - `AssignmentCard`: карточка задания с названием-ссылкой, курсом, бейджами статуса и сложности, дедлайном с проверкой просрочки (бейдж «Просрочено») и ссылкой перехода.
   - `AssignmentDetailsPage`: страница детального просмотра задания по параметру `:id` из `useParams`, отображением всех полей задания, ссылкой возврата к списку, а также корректным экраном «Задание не найдено» при неверном ID. Текст ссылок возврата нормализован (`К списку заданий`).
   - `NewAssignmentPage`: страница создания задания с явной текстовой заглушкой реализации формы в ЛР 3 и ссылкой возврата `К списку заданий`.
   - `NotFoundPage`: страница ошибки 404 для неизвестных маршрутов со ссылкой возврата к списку `К списку заданий`.

4. **Маршрутизация и стили (`src/App.tsx`, `src/App.css`, `src/main.tsx`):**
   - Корневой редирект `<Navigate to="/assignments" replace />`.
   - Маршруты: `/assignments`, `/assignments/new`, `/assignments/:id`, `*`.
   - Обертка `<BrowserRouter>` в `main.tsx`.
   - Современные адаптивные стили (CSS Grid с автозаполнением `minmax(280px, 1fr)`, адаптация для экранов вплоть до 360px, стилизация `focus-visible`, перенос длинных слов через глобальный `overflow-wrap: anywhere`).

## ЛР 3. Формы и локальное состояние приложения

Реализован локальный CRUD для сущности «Учебное задание» (`Assignment`), переиспользуемая форма с валидацией, фильтрация по статусу и явное уведомление о хранении данных в оперативной памяти:

1. **Типизация и валидация (`src/types/assignment.ts`):**
   - Тип `AssignmentDraft = Omit<Assignment, 'id'>` для представления создаваемого или редактируемого задания без идентификатора.
   - Константа `EMPTY_ASSIGNMENT_DRAFT` со значениями по умолчанию: пустое название и описание, дефолтный курс из справочника `COURSES[0]`, пустой дедлайн, статус `todo`, сложность `medium`.
   - Функция валидации `validateAssignmentDraft(draft)`: проверка названия (от 3 до 100 символов), обязательного срока сдачи (в формате ГГГГ-ММ-ДД), курса из справочника, диапазона сложности и предметного правила (для статуса `done` обязательно описание не короче 5 символов).

2. **Поднятие состояния и CRUD (`src/App.tsx`):**
   - Состояние `assignments` поднято в корневой компонент `App` с инициализацией копиями из `ASSIGNMENTS`.
   - Функция `createAssignment(draft)`: генерирует стабильный UUID через `crypto.randomUUID()`, неизменяемо добавляет запись в конец массива и возвращает созданный `id`.
   - Функция `updateAssignment(id, draft)`: неизменяемо обновляет запись через `.map()`, сохраняя исходный `id`.
   - Функция `deleteAssignment(id)`: неизменяемо исключает запись через `.filter()`.
   - Прямой импорт `ASSIGNMENTS` исключён из страниц `AssignmentsPage` и `AssignmentDetailsPage`; данные и колбэки передаются через props.
   - Маршрутизация расширена добавлением маршрута `/assignments/:id/edit` с компонентом `EditAssignmentPage`.

3. **Переиспользуемый компонент формы (`src/components/AssignmentForm.tsx`):**
   - Единая форма для создания и редактирования заданий с интерфейсом `AssignmentFormProps` (`initialValues`, `onSave`, `onCancel`).
   - Изолированное локальное состояние черновика (`useState<AssignmentDraft>`), предотвращающее мутацию внешних данных до отправки формы (отмена не затрагивает исходный объект).
   - Управляемые поля ввода: название (input text), курс (select с синхронным заполнением `courseId` и `courseTitle`), дедлайн (input date), статус (select), сложность (select), описание (textarea).
   - Доступность: атрибут `noValidate`, вывод ошибок валидации с `role="alert"`, кнопки с явными типами `type="submit"` и `type="button"`.

4. **Страницы создания и редактирования (`src/pages/`):**
   - `NewAssignmentPage`: отображает `AssignmentForm` со значениями по умолчанию `EMPTY_ASSIGNMENT_DRAFT`. При сохранении вызывает `onCreate` и переходит на страницу созданного задания `/assignments/${id}`. При отмене возвращает к списку.
   - `EditAssignmentPage`: извлекает `:id` через `useParams`, находит задание в общем списке. При отсутствии выводит экран «Задание не найдено». При наличии рендерит форму с атрибутом `key={assignment.id}`, что гарантирует сброс черновика при переходе между записями. Сохранение вызывает `onUpdate` с сохранением прежнего ID.

5. **Просмотр и удаление (`src/pages/AssignmentDetailsPage.tsx`):**
   - Кнопка перехода к редактированию «Редактировать» (`/assignments/:id/edit`).
   - Кнопка «Удалить» с модальным подтверждением `window.confirm(`Удалить задание «${assignment.title}»?`)` и последующим редиректом на `/assignments` (`replace: true`).

6. **Страница списка и фильтрация (`src/pages/AssignmentsPage.tsx`):**
   - Локальный фильтр по статусу задания (`useState<AssignmentStatus | 'all'>('all')`).
   - Подсчет статистики `calculateAssignmentStats` ведётся по полному списку заданий независимо от выбранного фильтра.
   - Разделение двух пустых состояний:
     - Список заданий пуст (`assignments.length === 0`): сообщение «Заданий пока нет.» и кнопка создания первого задания.
     - Фильтр не дал результатов (`visibleAssignments.length === 0` при наличии заданий): сообщение «Нет заданий с выбранным статусом.» и кнопка «Сбросить фильтр».

7. **Уведомление о хранении в памяти (`src/app/AppLayout.tsx`, `src/App.css`):**
   - Информационная плашка в `AppLayout` с пояснением: данные сохраняются временно в оперативной памяти и сбросятся при перезагрузке (F5); постоянное хранилище появится при подключении Supabase.
   - Стили для формы, полей ввода, ошибок, фильтра, кнопок и адаптивной раскладки для мобильных устройств.

8. **Тестирование (`test/integrity.test.ts`):**
   - Добавлены тесты для `EMPTY_ASSIGNMENT_DRAFT`, валидатора `validateAssignmentDraft` (включая предметное правило), неизменяемости операций CRUD и корректности фильтрации по статусам.

## ЛР 4. Загрузка справочника приложения по HTTP

В рамках лабораторной работы 4 реализована сетевая загрузка справочника курсов по HTTP с runtime-валидацией данных, управлением жизненным циклом запроса через пользовательский хук и интеграцией в форму создания и редактирования заданий:

1. **Статический JSON-справочник (`frontend/public/demo/courses.json`):**
   - Размещён в каталоге `frontend/public/demo/courses.json` и раздаётся dev-сервером Vite по адресу `/demo/courses.json` (при сборке проекта автоматически копируется в `dist/demo/courses.json`).
   - Содержит 5 курсов с уникальными строковыми идентификаторами (`c1`–`c5`) и понятными наименованиями (`name`):
     ```json
     [
       { "id": "c1", "name": "Веб-разработка" },
       { "id": "c2", "name": "Базы данных" },
       { "id": "c3", "name": "Операционные системы" },
       { "id": "c4", "name": "Алгоритмы и структуры данных" },
       { "id": "c5", "name": "Компьютерные сети" }
     ]
     ```

2. **Типизация справочника (`src/types/course.ts`):**
   - Определен контракт `Course`:
     ```ts
     export type Course = {
       id: string
       name: string
     }
     ```
   - В `src/data/courses.ts` справочник `COURSES` расширен интерфейсом `StaticCourse extends Course` с сохранением свойств `code`, `title` и `description` для обратной совместимости с существующими тестами и карточками.

3. **HTTP-сервис (`src/services/courses.ts`):**
   - Функция валидации одного элемента `isCourse(value: unknown): value is Course`: проверяет, что передан объект, `id` — непустая строка без ведущих/хвостовых пробелов (`value.id === value.id.trim()`), а `name` — непустая строка.
   - Функция разбора массива `parseCourses(value: unknown): Course[]`: проверяет тип массива и валидность всех элементов через `isCourse`, а также гарантирует отсутствие дублирующихся `id` (выбрасывает понятные ошибки `Неверная структура справочника курсов.` или `В справочнике повторяются идентификаторы.`).
   - Асинхронная функция `getCourses(signal?: AbortSignal)`: запрашивает URL `${import.meta.env.BASE_URL}demo/courses.json` через `fetch` с `cache: 'no-store'`, проверяет `response.ok` (с выбросом ошибки HTTP-статуса при сбое) и разбирает полученный JSON через `parseCourses`.

4. **Пользовательский хук жизненного цикла (`src/hooks/useCourses.ts`):**
   - Управляет состояниями загрузки через размеченное объединение:
     ```ts
     export type CoursesLoad =
       | { status: 'loading' }
       | { status: 'error'; message: string }
       | { status: 'success'; data: Course[] }
     ```
   - Запускает загрузку в `useEffect` с `AbortController` и флагом `active = true`. Функция очистки эффекта (`return () => { active = false; controller.abort(); }`) предотвращает обновление состояния размонтированного компонента или при повторной попытке.
   - Экспортирует `{ load, retry }`. Функция `retry()` переводит состояние в `loading` и инициирует новую попытку запроса, не перезагружая страницу целиком и не затрагивая черновик формы.

5. **Интеграция в форму заданий (`src/components/AssignmentForm.tsx`, `src/types/assignment.ts`):**
   - Константа `EMPTY_ASSIGNMENT_DRAFT` обновлена: `courseId: ''` и `courseTitle: ''` согласно Шагу 3 ЛР 4 («В пустом черновике оставьте tag: пустая строка, чтобы пользователь явно выбрал значение»). Новая форма открывается со значением «Выберите курс», а сохранение заблокировано до явного выбора курса.
   - Заменён статический справочник на вызов хука `useCourses()`.
   - Вычисляются вспомогательные значения:
     - `courses = load.status === 'success' ? load.data : []`
     - `selectedCourseExists = courses.some((c) => c.id === draft.courseId)`
     - `canSave = load.status === 'success' && selectedCourseExists`
   - Селектор курсов блокируется во время загрузки или при пустом справочнике.
   - Если в черновике указан идентификатор курса, отсутствующий в справочнике (`draft.courseId !== '' && !selectedCourseExists`), выводится заблокированная опция `Текущий код: {draft.courseId} — выберите доступный курс` и информационное предупреждение.
   - Под полем выбора курсов визуализируются все состояния:
     - Ожидание: `<p role="status">Загружаем курсы…</p>`
     - Ошибка: `<p role="alert">{load.message}</p>` и кнопка `<button type="button" onClick={retry}>Повторить</button>`
     - Пустой результат: `<p role="status">Курсов пока нет. Сохранение недоступно.</p>` и кнопка `<button type="button" onClick={retry}>Повторить</button>`
   - Кнопка «Сохранить» имеет атрибут `disabled={!canSave}`. В `handleSubmit` встроена защита `if (!canSave) { setError('Дождитесь справочника и выберите доступный курс.'); return; }`.
   - Черновик задания (название, описание, дата, статус, сложность) сохраняется между повторами запроса, а кнопка «Отмена» остаётся рабочей во всех состояниях сети.

6. **Тестирование целостности (`test/integrity.test.ts`):**
   - Добавлены 5 новых интеграционных тестов (суммарно 13 тестов):
     - `isCourse` (все валидные и невалидные сценарии, пробелы, пустые значения).

## ЛР 5. Схема данных и справочник в Supabase

В рамках лабораторной работы 5 спроектирована и внедрена реляционная схема базы данных в PostgreSQL через Supabase, справочник курсов перенесён из локального учебного JSON в удалённую базу данных, настроены права доступа PostgreSQL и Row Level Security (RLS), а веб-клиент переключён на официальную библиотеку `@supabase/supabase-js`:

1. **Схема базы данных и ограничения (`supabase/migrations/202610260001_initial_schema.sql`):**
   - Таблица справочника `public.courses`:
     - `id text primary key`: уникальный стабильный строковый идентификатор курса (`c1`–`c5`).
     - `name text not null unique`: читаемое наименование курса.
     - `constraint courses_id_not_blank check (id = btrim(id) and id <> '')`: запрет пустого идентификатора и пробельных символов по краям.
     - `constraint courses_name_not_blank check (name = btrim(name) and name <> '')`: запрет пустого или состоящего только из пробелов названия курса.
   - Основная таблица сущностей `public.assignments`:
     - `id uuid primary key default gen_random_uuid()`: первичный ключ записи типа UUID.
     - `owner_id uuid not null references auth.users(id) on delete cascade`: внешний ключ, привязывающий задание к пользователю системы аутентификации Supabase (`auth.users`), с каскадным удалением заданий при удалении пользователя.
     - `course_id text not null references public.courses(id) on update cascade on delete restrict`: внешний ключ к справочнику курсов с запретом удаления используемого курса (`restrict`) и каскадным обновлением ID.
     - `title text not null`: название задания.
     - `description text not null default ''`: подробное описание задания.
     - `status text not null`: статус выполнения (`todo`, `in_progress`, `done`).
     - `due_date date not null`: календарный дедлайн.
     - `difficulty text not null`: уровень сложности (`easy`, `medium`, `hard`).
     - `created_at timestamptz not null default now()`: временная метка создания записи.
     - Ограничения CHECK:
       - `assignments_title_length check (char_length(btrim(title)) between 3 and 100)`
       - `assignments_status_allowed check (status in ('todo', 'in_progress', 'done'))`
       - `assignments_difficulty_allowed check (difficulty in ('easy', 'medium', 'hard'))`

2. **Управление доступом, RLS и безопасность:**
   - RLS включён на обеих таблицах:
     - `alter table public.courses enable row level security;`
     - `alter table public.assignments enable row level security;`
   - Отозваны все права у клиентских ролей `anon` и `authenticated`:
     - `revoke all on table public.courses from anon, authenticated;`
     - `revoke all on table public.assignments from anon, authenticated;`
   - Для публичного справочника курсов выдано строго право чтения и создана политика выборки:
     - `grant select on table public.courses to anon, authenticated;`

   - Клиентские операции `INSERT`, `UPDATE`, `DELETE` для справочника запрещены (нет соответствующих GRANT и политик).
   - Таблица `public.assignments` оставлена закрытой от клиентских ролей до ЛР 6: RLS активирован, но политики и GRANT для `anon`/`authenticated` отсутствуют. Браузер не может читать или модифицировать личные записи.

### Вопросы для защиты ЛР 5

1. **Чем primary key отличается от foreign key?**
   - *Primary key* (первичный ключ) уникально идентифицирует каждую строку внутри своей таблицы и не может быть NULL (например, `id` в `courses` и `assignments`).
   - *Foreign key* (внешний ключ) связывает строку одной таблицы со строкой другой таблицы и гарантирует ссылочную целостность (например, `course_id` ссылается на существующий `courses.id`, а `owner_id` — на пользователя `auth.users`). База данных запрещает сохранять ссылку на несуществующую запись.

2. **Зачем проверять поля и в форме, и ограничениями БД?**
   - Валидация в форме обеспечивает быстрый, понятный и дружелюбный отклик для пользователя непосредственно в интерфейсе, предотвращая заведомо некорректную отправку.
   - Ограничения БД (CHECK, NOT NULL, UNIQUE, FK) обеспечивают строгую гарантию целостности данных на уровне хранилища независимо от того, откуда пришёл запрос — через браузер, сторонний API-клиент или скрипт.

3. **Почему id справочника должен оставаться стабильным при изменении name?**
   - На первичный ключ `id` (`'c1'`, `'c2'`) ссылаются внешние ключи других таблиц (`assignments.course_id`). Если `id` стабилен, то отображаемое название курса (`name`) можно переименовывать (например, «Веб-разработка» → «Веб-разработка на React») без нарушения ссылочной целостности и без необходимости обновлять миллионы связанных записей.

4. **Чем GRANT отличается от политики RLS?**
   - `GRANT` — это базовые привилегии PostgreSQL на уровне всей таблицы (право выполнять команды `SELECT`, `INSERT`, `UPDATE`, `DELETE`).
   - Политика `RLS` (Row Level Security) определяет фильтрацию на уровне конкретных строк таблицы (какие именно строки разрешено видеть или изменять субъекту).
   - Для доступа к данным требуется одновременное выполнение обоих условий: роль должна обладать правом `GRANT` и соответствующей разрешающей политикой RLS (`USING`).

5. **Почему личная таблица закрыта до ЛР 6?**
   - Таблица `assignments` хранит личные данные пользователей с привязкой к `owner_id uuid references auth.users(id)`. В ЛР 5 аутентификация пользователей ещё не настроена, поэтому открытие клиентского доступа сделало бы персональные данные уязвимыми. До подключения защищённой аутентификации Supabase Auth и политик `auth.uid() = owner_id` в ЛР 6 таблица остаётся заблокированной.

6. **Почему publishable key можно использовать в браузере, а secret key нельзя?**
   - `publishable key` (или `anon key`) предназначен для идентификации клиентского приложения. Он безопасен для размещения в браузере, поскольку все операции с ним строго ограничены правами PostgreSQL и политиками Row Level Security (RLS).
   - `secret key` (или legacy `service_role key`) обладает административными привилегиями и полностью обходит RLS. Если он попадёт в браузер, любой пользователь сможет прочитать, изменить или удалить любые данные в базе данных.

7. **Зачем хранить миграцию и seed, если таблицы уже созданы в Dashboard?**
   - Ручные действия в веб-интерфейсе Dashboard невозможно воспроизвести в другом окружении, протестировать в CI/CD или передать преподавателю/коллегам.
   - Файлы миграций (`supabase/migrations/`) и seed (`supabase/seed.sql`) фиксируют схему и начальные данные в системе контроля версий Git как код («Database as Code»), позволяя гарантированно развернуть базу данных с нуля на любом проекте.

8. **Как вы доказали, что форма читает Supabase и не использует старый JSON?**
   - Статический файл `frontend/public/demo/courses.json` полностью удалён из проекта.
   - Во вкладке Network браузера фиксируется сетевой GET-запрос к REST API Supabase (`https://<project-id>.supabase.co/rest/v1/courses?select=id%2Cname&order=name.asc`).
   - При изменении названия курса в Supabase через SQL Editor и нажатии кнопки «Обновить справочник» форма мгновенно отображает новое имя курса, полученное из базы данных.

## ЛР 6. Авторизация и сохранение личных записей

Реализована аутентификация пользователей через Supabase Auth (по email и паролю), защищены личные маршруты приложения и осуществлен полный перенос личных заданий (`assignments`) из временной оперативной памяти React в постоянную базу данных PostgreSQL в Supabase с разграничением прав на уровне строк (Row Level Security).

### Выполненные задачи и архитектурные решения

1. **Настройка Authentication в Supabase Dashboard:**
   - В разделе **Authentication** → **Providers** включён и настроен провайдер **Email**.
   - В разделе **Authentication** → **URL Configuration** заданы:
     - **Site URL**: `http://localhost:5173`
     - **Redirect URLs**: `http://localhost:5173/**`, `http://localhost:5173`
   - Подтверждение email сохранено включённым (в соответствии с регламентом практикума). При регистрации без мгновенной сессии форма выводит понятное указание подтвердить почту по ссылке из письма.

2. **Миграция политик владельца (`supabase/migrations/202611020001_assignments_owner_policies.sql`):**
   - Предыдущая миграция ЛР 5 (`202610260001_initial_schema.sql`) осталась неизменной для сохранения воспроизводимости истории.
   - Для таблицы `public.assignments` установлено значение владельца по умолчанию:
     `alter table public.assignments alter column owner_id set default auth.uid();`
   - Базовые привилегии отозваны от `anon` и `authenticated`, после чего роли `authenticated` выданы права на четыре базовые операции:
     `grant select, insert, update, delete on table public.assignments to authenticated;`
   - Спроектированы и применены 4 независимые политики RLS (отказ от обобщённой политики `FOR ALL`):
     - `assignments select own`: `for select to authenticated using ((select auth.uid()) is not null and (select auth.uid()) = owner_id);`
     - `assignments insert own`: `for insert to authenticated with check ((select auth.uid()) is not null and (select auth.uid()) = owner_id);`
     - `assignments update own`: `for update to authenticated using ((select auth.uid()) is not null and (select auth.uid()) = owner_id) with check ((select auth.uid()) is not null and (select auth.uid()) = owner_id);` (совпадение `USING` и `WITH CHECK` защищает исходную строку от изменения чужими пользователями и запрещает передачу записи другому владельцу)
     - `assignments delete own`: `for delete to authenticated using ((select auth.uid()) is not null and (select auth.uid()) = owner_id);`

3. **Хук состояния авторизации (`frontend/src/hooks/useAuth.ts`):**

   - Реализует защиту от состояния гонки: если событие `onAuthStateChange` уже изменило статус с `checking`, запоздалый ответ `getSession` не перезаписывает актуальное состояние.

### Вопросы для защиты ЛР 6

1. **Чем пользователь отличается от сессии?**
   - *Пользователь* (`User`) — это долговременная запись учётной записи в системной таблице `auth.users`, обладающая стабильным идентификатором (`id`), адресом электронной почты и учётными данными.
   - *Сессия* (`Session`) — это временное состояние подтверждённого входа в клиентском приложении, содержащее криптографический JWT-токен доступа (`access_token`) с ограниченным временем жизни и токен обновления (`refresh_token`).

2. **Почему после signUp нельзя всегда считать пользователя вошедшим?**
   - Если в проекте включено подтверждение электронной почты, сервис Supabase создаёт учётную запись пользователя, но не возвращает валидную сессию (`session === null`). В этом случае пользователь должен сначала подтвердить владение почтовым ящиком, перейдя по одноразовой ссылке из входящего письма, и только затем выполнить процедуру входа.

3. **Зачем нужен отдельный статус checking?**
   - При открытии или перезагрузке страницы клиентской библиотеке `supabase-js` требуется некоторое время для асинхронного чтения токенов из `localStorage` и их валидации через вызов `getSession()`. Статус `checking` позволяет отображать нейтральный экран ожидания («Проверяем сессию…») и предотвращает преждевременный ошибочный редирект уже авторизованного пользователя на форму логина `/auth`.

4. **Почему RequireAuth не заменяет RLS?**
   - Компонент `RequireAuth` работает исключительно на стороне браузера (клиентский рендеринг React Router) и предназначен для удобства навигации пользователя. Любой злоумышленник может отправить HTTP-запрос к API Supabase напрямую с помощью curl или консоли браузера в обход пользовательского интерфейса. Подлинным барьером безопасности выступают политики Row Level Security (RLS) в PostgreSQL, проверяющие токен пользователя на каждом SQL-запросе.

5. **Чем USING отличается от WITH CHECK?**
   - Условие `USING` применяется к уже существующим строкам таблицы: оно определяет, какие строки разрешено прочитать командой `SELECT`, изменить командой `UPDATE` или удалить командой `DELETE`.
   - Условие `WITH CHECK` применяется к новым и модифицированным строкам: оно проверяет допустимость вставляемых данных при `INSERT` и результирующих строк при `UPDATE`.

6. **Почему UPDATE требует также SELECT policy?**
   - В PostgreSQL для выполнения команды `UPDATE` с включённым RLS СУБД должна сначала прочитать исходную строку, проверив её доступность через условие `USING`, а затем (при наличии оператора `RETURNING` или для формирования ответа PostgREST) вернуть обновлённую запись клиенту, для чего необходима действующая политика `SELECT`.

7. **Как список очищается при выходе и смене аккаунта?**
   - В хуке `useEffect` компонента `App` смена `userId` или переход статуса авторизации в `guest` / `checking` сопровождается немедленным синхронным вызовом `setAssignments([])`, что гарантирует мгновенную очистку массива в памяти React до отправки или завершения нового сетевого запроса.

8. **Как вы доказали, что пользователь B не может изменить запись A?**
   - Попытка выполнить запрос `UPDATE` или `DELETE` с идентификатором строки пользователя A из сессии пользователя B фильтруется политикой RLS `using (auth.uid() = owner_id)`. СУБД возвращает успешный статус операции с количеством затронутых строк, равным нулю, не изменяя запись в базе данных и не раскрывая факт её существования пользователю B.
