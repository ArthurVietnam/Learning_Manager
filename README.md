# Учебный менеджер

Веб-приложение для ведения личных учебных заданий по фиксированным курсам. Проект выполняется в рамках лабораторного практикума «Практический курс веб-разработки: React, TypeScript, Node и Supabase» (ПГУ им. Т.Г. Шевченко, Физико-технический институт).

**Автор:** Мунтян Артур Олегович, группа 24ПИ1

## Тема и основной сценарий

Учебный менеджер помогает студенту вести личные задания по своим курсам. Пользователь регистрируется или входит по email и паролю, работает со своими личными заданиями (создание, чтение, редактирование, удаление), фильтрует их по статусу, отслеживает сроки сдачи и выходит из учётной записи.

Данные приложения разделены на две сущности:
1. `courses` — публичный справочник учебных курсов в Supabase (доступен для чтения всем).
2. `assignments` — личные записи заданий пользователя в Supabase, защищённые на уровне PostgreSQL через Row Level Security (доступны только владельцу `owner_id = auth.uid()`).

## Модель доступа и схема данных в Supabase (ЛР 6)

Схема базы данных состоит из публичного справочника курсов и защищённой таблицы личных заданий:

| Таблица | Назначение | Ключи и связи | Доступ и RLS-политики |
| :--- | :--- | :--- | :--- |
| `public.courses` | Публичный справочник учебных курсов | `id text primary key` (PK) | **Публичный (чтение всем)**: RLS включён; `grant select to anon, authenticated`; политика `"courses are publicly readable"` `using (true)`. Модификация клиентам запрещена. |
| `public.assignments` | Личные задания пользователей (основная сущность) | `id uuid primary key default gen_random_uuid()` (PK)<br>`owner_id uuid default auth.uid() references auth.users(id) on delete cascade` (FK)<br>`course_id text references public.courses(id) on update cascade on delete restrict` (FK) | **Строго личный (только владелец)**: RLS включён; `revoke all from anon, authenticated; grant select, insert, update, delete to authenticated`. 4 отдельные политики: `"assignments select own"`, `"assignments insert own"`, `"assignments update own"`, `"assignments delete own"` с условием `auth.uid() = owner_id`. |

### Модель доступа (Access Model)

- `courses` читают все пользователи (гости `anon` и авторизованные `authenticated`), изменения запрещены.
- `assignments` читает и изменяет **только владелец строки**:
  - `SELECT`: `using ((select auth.uid()) is not null and (select auth.uid()) = owner_id)`
  - `INSERT`: `with check ((select auth.uid()) is not null and (select auth.uid()) = owner_id)` (по умолчанию `owner_id` выставляется сервером как `auth.uid()`)
  - `UPDATE`: `using ((select auth.uid()) is not null and (select auth.uid()) = owner_id) with check ((select auth.uid()) is not null and (select auth.uid()) = owner_id)` (запрещает менять чужую запись и передавать свою запись другому пользователю)
  - `DELETE`: `using ((select auth.uid()) is not null and (select auth.uid()) = owner_id)`
- Гостевая роль `anon` не имеет никаких прав на таблицу `assignments`.

### Предметные ограничения схемы (CHECK constraints)

- **`public.courses`**:
  - `courses_id_not_blank`: `check (id = btrim(id) and id <> '')` — идентификатор не может быть пустым или содержать пробелы по краям.
  - `courses_name_not_blank`: `check (name = btrim(name) and name <> '')` — название курса обязательно, не пустое, уникальное (`unique`).
- **`public.assignments`**:
  - `assignments_title_length`: `check (char_length(btrim(title)) between 3 and 100)` — длина названия от 3 до 100 символов.
  - `assignments_status_allowed`: `check (status in ('todo', 'in_progress', 'done'))` — допустимые статусы задачи.
  - `assignments_difficulty_allowed`: `check (difficulty in ('easy', 'medium', 'hard'))` — допустимые уровни сложности задачи.
  - `description text not null default ''` — описание задания со значением по умолчанию.
  - `due_date date not null` — календарный срок сдачи.
  - `created_at timestamptz not null default now()` — точное время создания записи.

## Переменные окружения

Конфигурация подключения к Supabase осуществляется через переменные окружения с префиксом `VITE_`:

- `VITE_SUPABASE_URL` — HTTPS-адрес проекта Supabase (например, `https://abcdefghijkl.supabase.co`).
- `VITE_SUPABASE_PUBLISHABLE_KEY` — публичный анонимный API-ключ (`anon` / `publishable key`).

Шаблон переменных сохранён в файле `frontend/.env.example`:

```env
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_your_key
```

> **Правила безопасности:**
> - Локальный файл `frontend/.env.local` добавлен в `.gitignore` и **ни при каких условиях не коммитится в Git**.
> - В браузер попадают только публичные переменные с префиксом `VITE_`.
> - Использование секретных ключей (`secret key`, legacy `service_role`) или пароля БД во frontend, коде или тестах **строго запрещено**.

## Инструкция по развертыванию в Supabase

1. **Создание проекта и настройка Authentication**:
   - Войдите в [Supabase Dashboard](https://supabase.com/dashboard).
   - В разделе **Authentication** → **Providers** убедитесь, что включён вход по **Email**.
   - В разделе **Authentication** → **URL Configuration**:
     - Задайте **Site URL** для локальной разработки: `http://localhost:5173`.
     - Добавьте в список **Redirect URLs**: `http://localhost:5173/**` и `http://localhost:5173`.
   - Если включено подтверждение email (**Confirm email**), при регистрации форма приложения покажет инструкцию с просьбой подтвердить email по ссылке из письма.
2. **Применение миграции схемы ЛР 5**:
   - В Dashboard откройте **SQL Editor** и примените `supabase/migrations/202610260001_initial_schema.sql`.
   - Заполните справочник курсов из `supabase/seed.sql`.
3. **Применение миграции политик владельца ЛР 6**:
   - В **SQL Editor** создайте новый запрос и выполните миграцию `supabase/migrations/202611020001_assignments_owner_policies.sql`.
   - Скрипт назначит значение по умолчанию `owner_id set default auth.uid()`, выдаст права `select, insert, update, delete` роли `authenticated` и создаст 4 политики RLS для `public.assignments`.
4. **Настройка локального окружения**:
   - В каталоге `frontend` создайте файл `.env.local` (на основе `.env.example`) и вставьте свои значения `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`.

## Маршруты и защита страниц

Маршрутизация реализована на React Router v7:

- `/` — перенаправление на `/assignments` (`<Navigate to="/assignments" replace />`).
- `/auth` — публичная страница аутентификации (`AuthPage`):
  - Переключение режимов «Вход» и «Регистрация».
  - Контролируемые поля email и пароля, обработка состояний ожидания (`pending`), ошибок и уведомлений.
  - Регистрация с сохранением redirect URL (`options: { emailRedirectTo: window.location.origin }`).
  - Вход через `supabase.auth.signInWithPassword`.
  - При попытке авторизованного пользователя открыть `/auth` выполняется перенаправление на `/assignments`.
- **Защищённые маршруты (обёрнуты в `RequireAuth`)**:
  - Пока сессия проверяется (`status === 'checking'`), отображается статусная плашка «Проверяем сессию…».
  - Если пользователь не авторизован (`status === 'guest'`), выполняется редирект на `/auth` с сохранением исходного пути в `state={{ from: location.pathname }}`.
  - `/assignments` — страница списка личных заданий (`AssignmentsPage`):
    - Загрузка заданий из Supabase через `getAssignments()`.
    - Карточки заданий, плашка статистики, локальный фильтр по статусу.
    - Обработка состояний загрузки, ошибок сети с кнопкой повтора и пустых состояний.
  - `/assignments/new` — страница создания задания (`NewAssignmentPage`):
    - Форма `AssignmentForm` с асинхронным `onSave`.
    - Блокировка кнопки сохранения во время выполнения Promise для исключения дублирования записей.
    - Сохранение черновика при ошибке отправки.
  - `/assignments/:id` — детальный просмотр задания (`AssignmentDetailsPage`):
    - Полная информация о задании, бейджи статуса, сложности и просрочки.
    - Кнопка «Удалить» с подтверждением через `window.confirm` и асинхронным запросом к Supabase.
  - `/assignments/:id/edit` — редактирование задания (`EditAssignmentPage`):
    - Форма `AssignmentForm` с предзаполненными данными задания.
- `*` — страница 404 (`NotFoundPage`) для неизвестных маршрутов.

В каркасе приложения (`AppLayout`) отображается email текущего пользователя и кнопка «Выйти» (`supabase.auth.signOut({ scope: 'local' })`). Временный баннер о хранении в оперативной памяти удалён.

## Сценарий проверки двумя аккаунтами (A и B)

1. **Регистрация и вход пользователя A**:
   - Открыть `/auth`, зарегистрироваться пользователем A (`user_a@example.com`).
   - Войти, создать два задания (например, «Лабораторная 5 по БД» и «Курсовой проект по сетям»).
   - Перезагрузить страницу (F5): задания загружаются из базы данных.
   - Отредактировать одно из заданий, скопировать его ID из адресной строки.
2. **Выход**:
   - Нажать кнопку «Выйти» в шапке.
   - Список заданий мгновенно очищается в `[]`.
   - Попытка открыть `/assignments` перенаправляет на `/auth`.
3. **Повторный вход пользователя A**:
   - Снова войти как пользователь A: все созданные задания на месте с сохранёнными изменениями.
4. **Вход пользователя B и изоляция данных**:
   - Выйти и войти как пользователь B (`user_b@example.com`).
   - В списке пользователя B отображается «Заданий пока нет» (записи пользователя A полностью скрыты).
   - Создать задание пользователя B (например, «Индивидуальное задание B»).
   - Перезагрузить страницу: отображается только задание пользователя B.
5. **Проверка защитных барьеров RLS**:
   - Попытка запросить или обновить чужой ID пользователя A из сессии пользователя B затрагивает 0 строк благодаря политике RLS (`USING`).
   - Попытка отправить при создании чужой `owner_id` пользователя A отклоняется базой данных правилом `WITH CHECK`.
6. **Возврат к пользователю A**:
   - Войти обратно как пользователь A: все записи пользователя A в сохранности, запись пользователя B не отображается.

## Вопросы для защиты ЛР 6

1. **Чем пользователь отличается от сессии?**
   - *Пользователь* (`User`) — это долговременная учётная запись в `auth.users` со стабильным уникальным `id`, адресом электронной почты и метаданными.
   - *Сессия* (`Session`) — это временное подтверждение факта успешного входа конкретного пользователя, содержащее короткоживущий токен доступа (`access_token`) и токен обновления (`refresh_token`).

2. **Почему после signUp нельзя всегда считать пользователя вошедшим?**
   - Если в настройках Supabase Auth включено подтверждение почты (**Confirm email**), вызов `signUp` создаёт пользователя, но сессия не выдаётся (`data.session === null`), пока пользователь не перейдёт по подтверждающей ссылке из письма.

3. **Зачем нужен отдельный статус checking?**
   - При первой загрузке или обновлении страницы клиент `supabase-js` асинхронно восстанавливает сохранённую сессию из хранилища браузера. До завершения этой проверки статус `checking` предотвращает ложный кратковременный редирект авторизованного пользователя на страницу `/auth`.

4. **Почему RequireAuth не заменяет RLS?**
   - `RequireAuth` — это лишь клиентский интерфейсный компонент на уровне React Router, отвечающий за удобство навигации. Любой пользователь может отправить сетевой запрос к REST API Supabase напрямую в обход браузерного интерфейса. Настоящую и надежную защиту данных обеспечивает только Row Level Security (RLS) внутри PostgreSQL.

5. **Чем USING отличается от WITH CHECK?**
   - `USING` применяется для существующих строк таблицы (фильтрует строки при `SELECT`, определяет разрешённые для изменения строки при `UPDATE` и удаляемые при `DELETE`).
   - `WITH CHECK` проверяет новые или модифицированные строки (при `INSERT` и `UPDATE`), гарантируя, что создаваемые или результирующие данные соответствуют правилам безопасности.

6. **Почему UPDATE требует также SELECT policy?**
   - В PostgreSQL для выполнения `UPDATE` с условием `WHERE` и RLS серверу требуется сначала найти и прочитать исходную строку через проверку `USING`, а затем вернуть изменённую строку клиенту (или подтвердить её наличие), для чего необходимы права на операцию выборки (`SELECT`).

7. **Как список очищается при выходе и смене аккаунта?**
   - В хуке `useEffect` состояние `assignments` немедленно устанавливается в пустой массив `[]` при смене `userId` или переходе статуса в `guest` / `checking`, ещё до того, как начнётся сетевой запрос для новой сессии.

8. **Как вы доказали, что пользователь B не может изменить запись A?**
   - Запрос `UPDATE` с `id` записи пользователя A, выполненный в контексте сессии пользователя B, отфильтровывается политикой RLS `using (auth.uid() = owner_id)`. Запрос завершается успешно, но затрагивает ровно 0 строк, не раскрывая существования чужого `id` и сохраняя исходную запись в неизменном виде.
